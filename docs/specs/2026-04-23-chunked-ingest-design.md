# Chunked ingest design — ZEB-154

**Date:** 2026-04-23
**Linear:** [ZEB-154](https://linear.app/zeblith/issue/ZEB-154)
**Depends on:** ZEB-146 (merged in harmony-client PR #51)
**Related follow-ups:** [ZEB-155](https://linear.app/zeblith/issue/ZEB-155), [ZEB-156](https://linear.app/zeblith/issue/ZEB-156)

---

## Goal

Lift the current ~1 MiB single-file ingest cap in the File Manager by routing
large files through `harmony-content`'s FastCDC chunker and the existing
`BundleBuilder`. A 4 MB MP3 that the ZEB-146 smoke test couldn't upload should
work after this change; so should any file up to ~32 GiB. The chunking must be
transparent to the UI — the File Manager still sees one "file" with a single
root CID.

## Context

`ingest_content` in `src-tauri/src/lib.rs` today computes a single
`ContentId::for_book(bytes, flags)` and rejects inputs where `bytes.len() >
MAX_PAYLOAD_SIZE` with `"file too large ({n} bytes, max {MAX_PAYLOAD_SIZE})"`.
`MAX_PAYLOAD_SIZE` is 1 MiB - 1.

Harmony's content model is already designed for multi-chunk files. The building
blocks exist:

- `harmony_content::chunker` — FastCDC with a `chunk_all(bytes, &config)` helper
  that returns content-defined byte ranges. Default config is 256 KiB min /
  512 KiB avg / ~1 MiB max.
- `harmony_content::cid::ContentId::for_book(data, flags)` — leaf CID over a
  single book payload. Rejects data exceeding `MAX_PAYLOAD_SIZE`.
- `harmony_content::cid::ContentId::for_bundle(bytes, &children, flags)` and
  `harmony_content::bundle::BundleBuilder` — parent CID over an ordered list
  of child CIDs. `MAX_BUNDLE_ENTRIES ≈ 32 K` (one CID per 32 bytes of bundle
  payload).
- `bundle::parse_bundle(bytes)` — inverse: read a bundle payload back into an
  ordered slice of child CIDs.

Nothing in the runtime or CID layer needs to change. The work is in the Tauri
command, the event-loop verb handlers, and tests.

## Scope decisions (brainstormed 2026-04-23)

**Q1 — File-size ceiling for v1; flat vs. nested bundles?**
**Chosen: flat bundles only, cap at ~32 GiB** (= `MAX_BUNDLE_ENTRIES ×
MAX_PAYLOAD_SIZE`). No nested-bundle support in this PR.

Rationale: nested bundles are purely a scaling decision — the CID algebra is
identical and flat bundles generated by v1 will continue to parse correctly if
nested support lands later. More importantly, nested-bundle support is the same
architectural problem as folder/directory support (directories ARE bundles of
bundles; 62-layer nesting is the CAS design target). Those land together in a
future PR, not this one.

**Q2 — Pin/unpin/burn cascade to leaves?**
**Chosen: cascade all three.** Pinning a root pins every descendant; unpinning
and burning symmetric. Simple rule: "a verb on a root acts on the whole file's
CIDs."

Rationale: without cascade, pinning a 400 MB file and having a leaf evict under
cache pressure silently breaks the file — a new class of bug chunking would
introduce. Cascading makes pin semantics correctness-safe. Unpin/burn cascade
has a known limitation when leaves are shared across roots (CDC dedup, shared
sub-bundles) — documented as future work under ZEB-156 (root-pin-set model).
For v1 with no sharing, naive cascade is correct.

**Q3 — Progress reporting for multi-chunk uploads?**
**Chosen: silent v1; progress UX deferred as a follow-up.** Most realistic
uploads are small enough that the existing upload-button spinner is adequate.
Progress events can land in a focused PR once 100+ MB uploads are common.

## Architecture overview

```
ingest a large file:
  chunks = chunker::chunk_all(bytes, DEFAULT_CONFIG)    # 256K / 512K / ~1M
  leaf_cids = [ContentId::for_book(&bytes[range], flags) for each range]
  for each (leaf_cid, chunk):
      send IngestRequest via existing channel, await reply   # serial
  (bundle_payload, root_cid) = BundleBuilder().add_all(leaf_cids).build_with_flags(flags)
  send IngestRequest for the bundle
  sidecar.insert(root_cid, file_name, total_size, ...)
  return root_cid
```

The sidecar (`ContentIndex`) stores only the root CID + total file size. UI
sees one file regardless of chunk count; `list_content` is unchanged.

Read path: `fetch_content` transparently recurses. Given a CID, it checks the
flags; if bundle, parses children, fetches each, concatenates in order.
Single-CID callers continue to work without knowing about chunking.

Pin/unpin/burn cascade: event-loop verb handlers walk the bundle tree locally
via the runtime's content store (`runtime.storage_tier().cache()`), applying
the verb to every descendant.

Single-blob fast path preserved: files with `len < MAX_PAYLOAD_SIZE` take the
existing ZEB-146 single-CID path with no chunking overhead.

## Ingest path

**Location:** `src-tauri/src/lib.rs::ingest_content` Tauri command.

**Size-dispatch:**

```rust
const FLAT_BUNDLE_MAX: u64 =
    (MAX_BUNDLE_ENTRIES as u64) * (MAX_PAYLOAD_SIZE as u64);

if meta.len() > FLAT_BUNDLE_MAX {
    return Err(format!(
        "file too large ({} bytes). v1 flat-bundle cap is {} bytes (~32 GiB). \
         Support for larger files lands with folder/nested-bundle support.",
        meta.len(),
        FLAT_BUNDLE_MAX,
    ));
}

if bytes.len() <= MAX_PAYLOAD_SIZE {
    // Existing single-book path — unchanged.
} else {
    // New chunked path (below).
}
```

**Chunked path:**

1. `let ranges = chunker::chunk_all(&bytes, &ChunkerConfig::DEFAULT)?` — returns
   `Vec<Range<usize>>`.
2. For each range:
   - `let cid = ContentId::for_book(&bytes[range], ContentFlags::default())?`
   - Send `IngestRequest { cid_hex: hex::encode(cid.to_bytes()),
     data: bytes[range].to_vec(), reply: oneshot }` through the existing
     `ingest_tx` channel; `.await` the reply.
   - Append `cid` to `leaf_cids`.
3. Build the bundle:
   - ```
     let mut builder = BundleBuilder::new();
     for cid in &leaf_cids { builder.add(*cid); }
     let (bundle_payload, root_cid) =
         builder.build_with_flags(ContentFlags::default())?;
     ```
4. One more `IngestRequest` for the bundle.
5. Sidecar insert: `ContentIndexEntry { cid: root_cid.to_bytes(),
   size_bytes: total_size, .. }`.
6. Return `IngestResult { cid: hex::encode(root_cid.to_bytes()), file_name,
   size_bytes: total_size }`.

**Serial, not parallel.** For a 400-chunk file, 400 serial round-trips at
sub-ms each is a few hundred ms — tolerable for v1. Parallel chunk ingest
is a future optimization (would require batching or channel-capacity tuning).

**No auto-pin on ingest.** Matches ZEB-146 semantics. Trade-off documented:
a large file under cache pressure could evict its own leaves after ingest
before the user pins it. Acceptable for v1; if it bites, auto-pin-on-ingest
is a follow-up toggle.

**No event-loop protocol changes.** The existing `IngestRequest` handles
both leaves and bundles as opaque `(cid_hex, data)` pairs — the CID header
tells `parse_subscription_event` how to route.

## Fetch path (transparent recursion)

**Location:** new helper in `src-tauri/src/event_loop.rs`, called from the
`fetch_rx` handler arm. The Tauri `fetch_content` command signature is
unchanged.

```rust
async fn fetch_recursive(session: &Session, cid: ContentId) -> Result<Vec<u8>, String> {
    // Mirror the existing fetch_rx key construction: one-hex-char
    // sharding prefix + full CID hex.
    let cid_hex = hex::encode(cid.to_bytes());
    let prefix = cid_hex.get(1..2).unwrap_or("");
    let key = format!("harmony/content/{prefix}/{cid_hex}");
    let bytes = fetch_via_zenoh(session, &key).await?;
    if matches!(cid.cid_type(), CidType::Bundle(_)) {
        let children = bundle::parse_bundle(&bytes)
            .map_err(|e| format!("malformed bundle: {e:?}"))?;
        let mut out = Vec::new();
        for child in children {
            out.extend_from_slice(&fetch_recursive(session, *child).await?);
        }
        Ok(out)
    } else {
        Ok(bytes)
    }
}
```

- **Serial recursion, Zenoh GET per CID.** For a 400-chunk file: 1 bundle GET
  + 400 leaf GETs. A few seconds worst case; parallel fetch is a future
  optimization.
- **Bundle detection via `ContentId` flags** — the CID header encodes
  book/bundle/stream. No heuristics, no re-parsing.
- **Buffer-in-memory reassembly.** Bounded by the 32 GiB file cap but not
  small. Streaming-to-disk reassembly is a follow-up (orthogonal to this PR,
  tracked alongside partial-range fetch from the ZEB-154 ticket's out-of-scope).
- **Nested-bundle forward-compat.** The walker is recursive; if we ever emit
  nested bundles (folders PR), fetching works without a rewrite.
- **Depth guard.** Defensively cap recursion at `MAX_BUNDLE_DEPTH = 62`; the
  write side enforces this already, so legitimate fetches can't trip it.

`export_content` reuses `fetch_tx` and picks up recursion for free. Self-
ingested content resolves locally because Zenoh queries hit our own
subscription handler for CIDs in our storage tier.

## Pin / unpin / burn cascade

**Location:** `ContentVerbRequest` handlers in `src-tauri/src/event_loop.rs`.

**Why the walk lives in the event loop:** the runtime's `ContentStore` is
reachable only from inside the event-loop task (via
`runtime.storage_tier().cache()`). Round-tripping every descendant through
the verb channel would N × the contention; walking inside the handler is a
single pass.

**Shared helper:**

```rust
/// Walk a CID's descendants using the runtime's local cache. Returns every
/// CID in the tree rooted at `cid` (including cid itself) in unspecified
/// order. Bundle payloads not in cache are silently skipped — their
/// descendants can't be acted on but that's strictly no-op.
fn collect_descendants(cache: &ContentStore, cid: ContentId) -> Vec<ContentId> {
    let mut out = Vec::new();
    let mut stack = vec![cid];
    while let Some(id) = stack.pop() {
        out.push(id);
        if matches!(id.cid_type(), CidType::Bundle(_)) {
            if let Some(bytes) = cache.get(&id) {
                if let Ok(children) = bundle::parse_bundle(bytes) {
                    stack.extend(children.iter().copied());
                }
            }
        }
    }
    out
}
```

**Handler pattern (pin):**

```rust
ContentVerbRequest::Pin { cid, reply } => {
    let root = ContentId::from_bytes(cid);
    let all = collect_descendants(runtime.storage_tier().cache(), root);
    let mut any_failed = false;
    for id in all {
        if !runtime.pin_content(id) { any_failed = true; }
    }
    let _ = reply.send(Ok(!any_failed));
}
```

Unpin mirrors this with `runtime.unpin_content(&id)` per descendant. Burn is
identical to Unpin at the runtime level; sidecar removal continues to happen
in the `burn_content` Tauri command (unchanged).

**Pin failure semantics:** `runtime.pin_content` returns `bool` (false = quota
exhausted). With cascade, "file is now pinned" requires every leaf pinned; if
any leaf fails, we return `Ok(false)` so the frontend's existing
`throw new Error('pin quota exhausted')` fires. Partial pin state is
tolerable — user can retry pin or unpin to clear.

**Fetch walker vs. cascade walker are not factored together.** They read from
different sources (local cache vs. Zenoh) with different failure modes.
Keeping them separate is clearer than a generic walker abstraction.

## Error handling and file-size cap

| Failure | Handling |
|---|---|
| File larger than `FLAT_BUNDLE_MAX` | Reject with cap-aware error message referencing the folder-support follow-up. |
| File read failure (`tokio::fs::read`) | Propagate as `"read failed: {e}"`. No cleanup — chunking hasn't started. |
| `chunker::chunk_all` error | Propagate with prefix. Shouldn't happen with `DEFAULT` config. |
| `ContentId::for_book` error on a leaf | Propagate, abort. Already-ingested leaves stay in cache unpinned, W-TinyLFU reclaims. |
| `IngestRequest` reply `Err` for a leaf | Propagate, abort. No sidecar entry written. |
| `BundleBuilder::build_with_flags` error | Propagate. In flat-only v1 this only trips on `leaf_cids.len() > MAX_BUNDLE_ENTRIES`, which is exactly the `FLAT_BUNDLE_MAX` guard — defense-in-depth. |
| `IngestRequest` reply `Err` for the bundle | Propagate. Leaves are orphaned in the cache (unpinned, no sidecar ref); W-TinyLFU reclaims. |
| `collect_descendants` can't read a bundle payload | Silent skip. Verb succeeds for reachable CIDs. |
| Fetch-side `parse_bundle` error | Propagate as `"malformed bundle"`. Stops recursion. |
| Fetch-side leaf GET error | Propagate. Partial fetches aren't useful. |

**Atomicity:** ingest is not transactional. A partial failure leaves orphaned
leaves in the cache. Acceptable — they're unpinned, absent from the sidecar,
W-TinyLFU reclaims them, no user-visible drift.

**No retry logic in v1.** A chunker or ingest failure indicates a
runtime-level problem; retrying would mask it. UI error handling (try/catch
from ZEB-146's review-feedback pass) covers the user-visible surface.

## Testing strategy

**Rust unit tests:**

1. **Size-threshold dispatch** — given a byte buffer of size
   `MAX_PAYLOAD_SIZE - 1`, chunked path is NOT taken; at
   `MAX_PAYLOAD_SIZE + 1`, chunked path IS taken. Helper that returns the
   CID-construction choice without running the full ingest pipeline.
2. **Bundle assembly from chunker output** — feed a synthetic 5 MiB buffer
   into `chunk_all` + per-range `ContentId::for_book` + `BundleBuilder::
   build_with_flags`. Assert: root CID is a bundle, children match the leaf
   CIDs in order, `parse_bundle` round-trips.
3. **`collect_descendants` correctness** — build a two-level bundle in a
   local `MemoryBookStore`, assert walker returns root + every descendant;
   single-book input returns `[cid]`; delete a bundle payload mid-walk,
   assert the unreachable subtree is silently skipped.
4. **File-size cap rejection** — assert the `FLAT_BUNDLE_MAX` guard fires
   with the expected error message at cap+1.

**Rust integration test** (extend
`src-tauri/tests/content_index_integration.rs`):

5. **Chunked ingest → pinned-set → pin cascade → fetch recursion → burn
   cascade** round-trip, analogous to the existing
   `ingest_list_pin_burn_roundtrip` but with a 3 MiB synthetic buffer
   (guaranteed to chunk into 3–6 leaves). Steps:
   - Generate 3 MiB of deterministic bytes.
   - Chunk locally, issue one `IngestRequest` per leaf + one for the bundle,
     insert sidecar entry for the root.
   - `PinnedSet` snapshot (empty), `Pin { root }`, `PinnedSet` snapshot
     (contains root + every leaf), fetch root via cache-backed helper that
     mirrors `fetch_recursive` (since the integration test skips
     Zenoh-dependent paths via the port-in-use graceful skip), assert
     reassembled bytes match the original.
   - `Burn { root }`, assert `PinnedSet` empty, assert sidecar removal.
6. **Inherits ZEB-146's port-in-use graceful skip** so the test is
   CI-stable.

**Non-goals in this PR's tests:**

- No Zenoh-network-path coverage for `fetch_recursive`. The existing
  `fetch_via_zenoh` is untouched; we're wrapping it. Zenoh-backed E2E is
  ZEB-150 territory.
- No UI-level tests for chunked upload. The TS wire format (`IngestResult
  { cid, fileName, sizeBytes }`) is identical for single-book and chunked
  paths. Existing `file-manager-service.test.ts` coverage stays valid.

**Manual smoke test at PR-finish time:**

- Upload the 4 MB MP3 from the ZEB-146 smoke test, verify it appears in the
  list.
- Pin, restart (expected: `pinned=false` per ZEB-155 — out of scope here).
- Export via the native save dialog, verify bytes-identical reassembly.

## Out of scope / follow-ups

- **Nested bundles + folders** — the architectural extension for files >32 GiB
  and directory structure. Same problem; lands together in a dedicated PR.
- **[ZEB-155](https://linear.app/zeblith/issue/ZEB-155): persist pin state
  across restart** — chunked ingest inherits the same limitation. The
  root-pin-set model ([ZEB-156](https://linear.app/zeblith/issue/ZEB-156)) is
  a natural fit for persistence.
- **[ZEB-156](https://linear.app/zeblith/issue/ZEB-156): root-pin-set cascade
  semantics** — the "correct" answer for pin/unpin/burn once leaves are
  shared across roots. Lands with folders.
- **Progress reporting** during multi-chunk ingest. Trivial to add once the
  protocol is stable.
- **Parallel chunk ingest / fetch** — v1 is serial. Worth revisiting if
  100+ MB uploads become common.
- **Streaming reassembly to disk** — for files approaching the 32 GiB cap.
  Also a prerequisite for partial-range fetch (ZEB-154's "4 TB file, touch a
  few MB" scenario, explicitly out of scope per the ticket).
- **Partial-range fetch** — fetch only some chunks of a bundle. Phase 2 work
  tied to on-disk offload and networking; out of scope per the ticket.
- **User-facing "inspect chunks" UI** — nice-to-have per the ticket, not
  required for transparent-chunking UX.
