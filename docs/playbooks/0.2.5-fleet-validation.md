# v0.2.5 pre-release fleet validation runbook

> **Status:** ready to run. Owner: fleet (Koya + Ildwyn + AVALON).
> **Goal:** prove, on real cross-WAN nodes, that the flows 0.2.4 broke actually
> work before we spend the 0.2.5 version number.

## Why this exists

v0.2.4 shipped with dealbreakers that **only manifest cross-WAN** — a fresh
identity was undiscoverable, peer names never resolved, reachability records
were silently dropped. They passed every same-machine test (the ZEB-878 mesh
exercise found them live). The 0.2.5 delta is almost entirely the fix-set for
those. This runbook re-proves each fix on the real mesh.

The single most important rule: **test a binary built at 0.2.5 HEAD.** Every
node currently running on the fleet is a stale build (0.2.4 or older) and would
validate the *broken* behavior.

## Delta under test (what 0.2.5 fixes)

| Area | Tickets | Was broken in 0.2.4 |
|---|---|---|
| Discoverability default | ZEB-881 / 890 / 893 / 894 | fresh identity OFF → no first cross-WAN contact |
| Member-card name resolution | ZEB-882 / 884 / 568 | peer name never resolved / ≤600s late-join latency |
| Reachability record size | ZEB-880 / 891 | record over pkarr cap → silently undiscoverable |
| Invite redemption | ZEB-888 / 889 / 885 / 892 | double-spend; failed-delivery invite unredeemable; prose errors |
| DM path hardening | ZEB-886 / 887 | malformed IDs → slow/opaque failures |
| Read receipts (headless) | ZEB-883 | verbs absent from `serve` allowlist |
| Sybil tunnel admission | ZEB-757 / 758 | one source could occupy all inbound slots |
| Masked-panic capture | ZEB-695 | zenoh SIGABRT erased the causal panic (diagnostic) |

## Step 0 — prerequisites (do not skip)

### 0.1 Build at HEAD and pin it
```bash
cd ~/work/zeblithic/harmony-client
git pull --ff-only origin main
git rev-parse --short HEAD                       # record this hash in results
cd src-tauri && cargo build --bin harmony-app    # ~280 MB debug binary
export HARMONY_APP_BIN="$PWD/target/debug/harmony-app"   # e2e-harness reads this
```
Redeploy any long-running fleet node onto this binary (the running ones are
`d8761cdf`=0.2.4 and older `c91087d9` — stale). Confirm with
`pgrep -fl harmony-app` that no stale build is still serving.

### 0.2 Topology — must be genuinely cross-WAN
Co-located (same-LAN) nodes let zenoh multicast mask the iroh path — the exact
trap that hid these bugs. Use ≥2 nodes on **different WANs**: Koya + Ildwyn +
AVALON, or the GCE xwan pair. Strip `HARMONY_ZENOH_ENABLE_LAN_SCOUTING` on every
node so the real peer path is forced (the e2e-harness does this automatically).

### 0.3 Cheap pre-filter first
Before cross-WAN effort, run the same-machine harness on the HEAD binary — it
catches any regression for free:
```bash
cd ~/work/zeblithic/harmony-client/e2e-harness
cargo nextest run --features e2e --test-threads 1     # HARMONY_APP_BIN must be exported
```
Green here is necessary, not sufficient — it can't see cross-WAN timing/NAT.

### 0.4 One-node bring-up (reference)
```bash
export HARMONY_PASSPHRASE_FILE=$HOME/.harmony-<profile>-pass
harmony-app --profile <profile> serve --api-port <port> &
harmony-app --profile <profile> api mint_owner_identity        # first boot only
# observe async results:
harmony-app --profile <profile> api --events                   # WS firehose
```
All verbs: `harmony-app --profile <p> api <verb> '<json-args>'`. Stdout is
result-JSON only (jq-safe); exit 0 ok / 1 server error / 2 local failure.

## Validation matrix

Run each on the cross-WAN topology. "A" and "B" are two owners on different
WANs. Record PASS/FAIL + observed timing in the results table.

### V1 — fresh identity is discoverable without a manual toggle (ZEB-881)
The headline fix. On a **freshly minted** B:
```bash
harmony-app --profile B api connectivity_pkarr_publication_status '{}'
#   expect { "identityActive": true, ... }   — with NO connectivity_set_identity_discoverable call
```
**PASS:** `identityActive:true` within ~90s of mint, zero manual enable.
**FAIL (blocker):** false → the 0.2.4 cliff survived.

### V2 — reachability record publishes and resolves (ZEB-880/891)
```bash
harmony-app --profile B api connectivity_get_my_reachability_record '{}'   # exists, within cap
harmony-app --profile A api connectivity_list_peer_reachability '{}'        # A sees B
```
**PASS:** B's record present on A; no "record too large / can't fit pkarr cap"
warning in B's boot log.

### V3 — first cross-WAN contact via invite (ZEB-881, mirrors e2e `s1`)
```bash
harmony-app --profile A api generate_invite '{"communityId":"<cid>"}'       # → invite url
harmony-app --profile B api connectivity_redeem_invite_iroh '{"url":"<url>"}'
# watch community-members-changed on both
```
**PASS:** both rosters converge (each `list_community_members` shows the other)
within a few minutes.

### V4 — member-card name resolves, fast, for a late joiner (ZEB-882/884/568)
After V3, on A (who joined earlier) subscribe to late-joiner B's card and vice-versa:
```bash
harmony-app --profile A api subscribe_member_card '{"ownerId":"<B-owner>"}'
harmony-app --profile A api get_cached_member_card '{"ownerId":"<B-owner>"}'
# watch member-card-received
```
**PASS:** display name (not truncated hex) resolves in **seconds**, not ≤600s.
This is the ZEB-878 finding — watch it specifically.

### V5 — invite robustness (ZEB-888/889)
- Redeem the **same** invite twice → second attempt rejected (single-use).
- Take an invite whose delivery failed once, retry → succeeds (redeemable).
**PASS:** double-spend rejected; failed-delivery invite still redeemable.

### V6 — structured redeem errors (ZEB-885/892)
```bash
harmony-app --profile B api connectivity_redeem_invite_iroh '{"url":"<bad-or-expired>"}'
```
**PASS:** error body carries a machine `code`, not just prose.

### V7 — read-receipt verbs work headless (ZEB-883)
```bash
harmony-app --profile A api set_space_read_receipt_pref '{"spaceId":"<sid>","enabled":true}'
harmony-app --profile A api mark_dm_read '{"spaceId":"<sid>"}'
harmony-app --profile A api get_space_read_receipt_pref '{"spaceId":"<sid>"}'
```
**PASS:** all three accepted on a `serve` node (were 404/absent in 0.2.4).

### V8 — DM path fails fast on bad input (ZEB-886/887)
```bash
harmony-app --profile A api send_dm '{"spaceId":"nothex","body":"x"}'   # expect fast typed reject
```
**PASS:** immediate structured rejection; no hang, no panic.

### V9 — no masked panics (ZEB-695, passive)
Set `HARMONY_PANIC_LOG=/tmp/harmony-panics-<node>.log` on each node before boot;
after the run, the file should be **empty**. Any record = a captured panic worth
filing (this is the diagnostic net working as intended).

### Regression smoke (already scripted as `s2/s4/s8/s9` — run if time permits)
Friend-add-by-key (also re-checks V1), channel multi-member exchange, presence
(`subscribe_community_presence` → `get_community_presence`), restart durability.

## Coverage note (not a blocker)

- **1:1 DM byte-delivery across owners is proven, not a gap.** Investigated and
  cleared: the e2e hard-assert `s2_dm_delivery_over_tunnel_hard_assert`
  (`e2e_two_node.rs:490`) is **not** ignored — it runs under `--features e2e`
  and hard-asserts both the `dm-received` event and plaintext read-back on the
  recipient (green 5/5). The historical `SpaceNotFound` carrier gap was closed
  by ZEB-473→482→484→**485** (Done, PR #275, 2026-06). CI-run integration test
  `community_relay_prod.rs:3433` covers the same semantics on every push. So
  **step 0.3 already exercises live cross-owner DM delivery**; the cross-WAN
  manual send below is a confirmation, not a blocker gate.
- **The whole e2e-harness suite runs in NO CI** (`--features e2e` is never set
  by `ci.yml`; no schedule). The integrated cross-WAN flows these V-checks cover
  are only guarded when a human runs them — which is *why* 0.2.4's dealbreakers
  reached a release. Recommended follow-up: a scheduled + dispatchable `e2e` CI
  runner (same-machine two-node) so these regressions surface automatically —
  not a 0.2.5 fix.
