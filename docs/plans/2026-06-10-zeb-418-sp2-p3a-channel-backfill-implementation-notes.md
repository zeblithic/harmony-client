# ZEB-418 SP2 P3a — Implementation Notes (deviations + discoveries)

Plan: `2026-06-10-zeb-418-sp2-p3a-channel-backfill-plan.md`. Commits T1–T6: `3849b1b0`, `2dc97c4a`, `70404345`, `fe75f1bf`, `8f0e2d81`, `88bb7490`.

1. **No-holder retry is unreachable over real zenoh (T6, spec §6 amended).** A GET with zero matched queryables completes as a clean empty reply stream — wire-indistinguishable from "a holder served nothing" — so the latch satisfies instead of backing off. In-session retry covers only genuine aborts (adapter teardown / GET failure → oneshot sender dropped → `RecvError` mapped to no-reply). No-holder healing = next engine start's watermark re-sync. Latch backoff coverage stays at the unit level (T4). Follow-up filed for in-session healing options (empty-marker reply, periodic re-sync, transport-recovery `reset()`).
2. **`run_backfill_driver`'s watermark closure is async** (T4 deviation from the plan sketch's sync `Fn() -> Option<Hlc>`): the log sits behind a `tokio::sync::Mutex`; a sync `try_lock` miss on a full page would leave `since` unchanged and spin the no-backoff paging loop.
3. **Page report shape** (T3, per plan note 4): `BackfillPageReport { replies, limit }` — the post-page watermark is re-read from the LOG (only verified events land there), so a hostile holder serving garbage cannot advance `since`. Report fires only on a clean stream close; abort paths drop the sender. Cross-config caveat: `replies < limit` means "no more pages" only under matched limits (pre-existing spec §6.2 behavior); effective limit = `min(backfill_default_limit [256], CHANNEL_BACKFILL_MAX_LIMIT [1000])`.
4. **Trigger 3 was already wired (T5, case a):** the ZEB-270 channel-config hook (`lib.rs:4206-4328`) routes mid-session remote `ChannelCreate` through `delta_to_channel_config_change` → `registry.spawn` → `spawn_inner_now`, where the T4 driver auto-starts. Test-only proof (`mid_session_new_channel_created_spawn_fires_backfill_since_none`); zero production change.
5. **Latch in-flight semantics (T2):** while a request is in flight, `next_action` returns `WaitUntil(max(next_retry_at, now))` — the driver polls again once an outcome lands; a degenerate full page with `max_hlc_seen: None` leaves `since` unchanged (immediate same-window re-request).
6. **Retry-base config knob (T6 prerequisite):** `ChannelLogEngineConfig.backfill_retry_base_ms` (default 30_000) → `BackfillLatch::new_with_backoff`; integration fixtures use 200 ms.
7. **Test-harness discovery (T6):** the queryable task's `biased` select re-creates its 1 s closing-poll sleep each iteration, so sub-second probe spacing can livelock a *stopped* queryable into serving stale events; fixture probes are spaced 1.1 s (`wait_until_serving`).
